## AUD-01 / INV-10 assessment — mandatory before any integration recommendation

PR [#8](https://github.com/elanmust-GFLOer/GFLO.Octo_PIE-cookR/pull/8) explicitly documents that the database owner can update a binding without appending audit. Its `b22/tests/02_pg_races.py::test_06_known_audit_gap_is_exposed` performs the privileged update and asserts the audit count is unchanged. Its PASS is successful **exposure of a defect**, not mandatory-audit enforcement.

The audit rewrite trigger and RLS do not transactionally require every owner binding mutation to emit an audit event. PostgreSQL owners/admins retain administrative power; NOLOGIN roles alone do not remove it. PR #12 improves the narrow definer path: separate owner/mutator roles, restricted caller DML, and transactionally coupled suspension/audit/request result. It still grants a mutator direct update privileges and uses caller-supplied identity arguments. That is not a global owner-resistant audit guarantee.

PR #14 revokes dangerous EXECUTE/DML and role-membership reachability for four operational roles; the full matrix remains in CI. It does **not** constrain database superusers, table owners, or a separately privileged mutator. PR #15 explicitly retains that boundary. PRs #16–#18 add no global database audit enforcement. Therefore **AUD-01 / INV-10 is OPEN for privileged-owner/global-audit claims**. It must not be declared closed by later green CI.

An eventual laboratory-only code promotion could retain that defect as a prominently documented, tested finding, provided reviewers explicitly approve the scope, quarantine is included, and the SQL cannot be auto-applied. Any staging/production recommendation requiring mandatory audit needs a separate privileged-administration threat model, trusted transactional entrypoints for operational paths, verified role/credential separation and, if hostile administrators are in scope, independently controlled audit/monitoring beyond owner-controlled tables. No such remediation or approval is supplied here.

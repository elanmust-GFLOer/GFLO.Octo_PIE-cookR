# Pilot 0C — offline synthetic EOA proof

Anchor: `e9e1c2f3ae599046ac7c16788a6b6aa1cea1534b` (draft PR #16).
No existing tracked file is changed. This is an additive, non-production library
and test package: no HTTP endpoint, production Auth connector, persistent wallet
binding, database migration, chain RPC, transaction, XP, token or app modification.

## Trust and data flow

Trusted fixture administration creates two independent synthetic principals and
profiles, opaque session handles in a WeakMap authority, a separate local
generation/suspension controller, an allowlist of known synthetic EOA addresses,
source references and a bounded pseudonymized audit sink. Client-asserted user,
profile or session IDs cannot construct a handle. These are not Supabase sessions.
The administrative fixture methods must never be exposed as application APIs.

`issue(handle, {wallet, source, requestId})` requires ACTIVE, unexpired session
authority and equal local generation in READY state. It creates a CSPRNG 256-bit
nonce, UUID challenge, 60-second expiration, canonical SIWE text and a separate
EIP-712 consent value. The session lasts 300 synthetic seconds; no JWT claim is
treated as session liveness. Missing authority, UNKNOWN and revoked/expired
sessions fail closed. Source/EOA metadata are trusted offline fixture inputs,
not proof of deployment or chain account type.

The SIWE signature proves EOA control using **ERC-191 personal-message signing**.
The separately required EIP-712 signature covers principal, profile, wallet,
chain, protocol reference and manifest digest, exact read scope, generation,
nonce, challenge ID, request ID, SIWE-message digest, expiry, consent version,
consent-text digest and synthetic Auth project. The typed domain binds a dedicated
name/version, chain and salt. It deliberately has no verifyingContract: this is
an off-chain observation, not a contract authorization. No signature is sent to
a contract. A SIWE signature never substitutes for signed consent.

`verify(handle, submission)` validates all message fields and canonical text,
both recovered EOA signers, exact server-issued consent and replay state. After
cryptographic verification it yields once, then prepares a deeply frozen result,
checks independent authority/generation/consent/replay, obtains audit approval,
and checks them again before atomic in-memory consumption and result return.
Concurrent identical attempts can succeed **once**. Foreign sessions/users
cannot consume a victim challenge. Audit callbacks that revoke or change epoch
cannot authorize a result. Audit failure releases no protected identity.

The final commit has no asynchronous gap between its last checks and consumption.
This is a **single Node event-loop, in-memory** ordering guarantee. There is no
PostgreSQL transaction, replica-wide replay protection, durable consent history,
cross-system Supabase revocation guarantee or recovery authorization. Process
restart loses records and refuses outstanding proofs; it does not restore them.
All requests require fresh verification; consumed/lost-response retries deny.
The bounded instance holds at most 256 challenges, and denies further admission;
there is no eviction that revalidates a consumed challenge or automatic retry.

## SIWE compatibility and supported wallets

The parser implements a strict EIP-4361 ABNF-compatible **subset** generated by
this service: ASCII, checksum address, one statement, HTTPS URI, version 1,
positive chain ID, nonce, UTC whole-second issued/expiration/not-before times,
UUID request ID and four URI resources. Optional fields are deliberately required
by this profile. Their order follows ERC-4361: expiry, not-before, request ID,
resources. No CRLF, unknown/duplicate fields, Unicode, alternate timestamp forms,
empty statement or omitted profile fields are accepted. This is not a universal
SIWE parser. Chain/domain/URI/nonce/time/resources must match the issued challenge.

Only 65-byte, low-s secp256k1 EOA signatures with canonical v=27/28 are accepted.
Compact EIP-2098, alternate v encodings, smart accounts, EIP-6492/counterfactual
accounts, delegated account semantics and hardware-wallet transports are not
supported. **ERC-1271 is NOT SUPPORTED**: there is no contract verification
adapter or call, so contract/unknown wallet types deny. Caller-supplied EOA labels
cannot alter the trusted synthetic wallet registry. No claim about a live
address's code or wallet type is made without chain evidence.

## Result and provenance boundaries

A result is a non-reusable, read-only historical observation with trace ID,
principal/profile, wallet/chain, exact signed source reference, generation,
scope, consent digest, evidence classifications and expiration. There is no
redeem-result API, binding activation or entitlement consumer. Every result,
including DENIED, has `productionAuthorized=false`, `canonicalXpAuthorized=false`,
empty entitlements and mutation capabilities, and `reusable=false`.

VERIFIED_WALLET_CONTROL means only that the synthetic EOA signed both expected
proofs. It proves neither unique humanity, account recovery, contribution
eligibility, canonical XP nor protocol privileges. Demo source metadata remains
DEMO_FIXTURE. The legacy Sepolia PIECore address is forcibly classified
LEGACY_UNTRUSTED_XP; its manifest digest identifies the **incomplete historical
Pilot 0B record**, not an accepted production source manifest. Referencing that
record in consent never closes its missing bytecode/proxy/freshness evidence.
No REVIEWED_PROTOCOL_DATA source or canonical PIE connector is enabled here.

Events contain only environment, trace/request IDs, bounded decision codes and
per-instance HMAC pseudonyms. No token, SIWE text, signature, wallet address,
profile or private key is logged. The sink holds 256 events. Approval is not a
data-receipt proof; final denial can follow an approval if authority changes.

## Deadline and secrets

This package does not modify the R6A.1 one-second gateway. Offline verification
also samples a one-second monotonic budget before crypto, after crypto, after
the concurrency yield and immediately around final audit/commit. Expiry and
non-monotonic time deny. There is no external asynchronous adapter or transport
and no unbounded wait/retry. Cryptography is synchronous and bounded by input
limits. The guard is not a hard real-time scheduler or network-delivery promise.

Each test creates fresh ephemeral EOA keys in its process. Key-bearing objects
remain inside signing closures; no key/mnemonic is serialized, exported, logged,
committed or used on a real network. Public specification vectors contain only
public addresses/signatures, never a private key. JavaScript does not guarantee
secret zeroization or constant-time execution; process isolation and ephemeral
use are laboratory restrictions, not production key-management certification.

historical independent audit scope, MIT notices and public test vectors.
The exact ethers distribution is vendored and hash-checked before loading.
No npm installation or live dependency lookup is needed to execute crypto.

Run: `node pilot0c/tests.cjs`. The exact JSON manifest pins **96** test identities;
failure output is sanitized to test name/status, never raw exceptions containing
signing inputs. Runtime/OpenSSL/library versions and per-test outcomes are written
to `evidence/pilot0c-ledger.json`. The declaration file is a reviewable interface
contract; no TypeScript compiler/typechecking execution is claimed.

The combined disposable gate runs the **unchanged 207 named regressions and all
SQL gates**, then the 96 crypto tests: **303 total**, zero skips/expected failures.
Provenance verifies every inherited Git blob, allowed additive paths, exact new
manifest, upstream library blob/hash, real checkout/merge parents/tree, Python
wheel versions and immutable Actions/PostgreSQL references. Node is pinned to
22.14.0 in CI; local execution uses 24.19.0. CI requires two fresh job-local
databases and never applies migrations to a real service. Actual results and
limitations must be read from the current run ledger, not this acceptance target.

Production remains **BLOCKED**. gfloDEVaccount remains NOT VERIFIED. No automatic
R6B, B2.4, wallet-binding activation, merge or deployment follows this pilot.
